# AI-experiments

実際の仕事や個人の活動を続けながら、テンプレート・スキル・ツールがどこで役立ち、どこで手直しが必要になるかを記録する。ケースは利用目的ごとに一つ作る。同じ目的で複数の対象を使う場合も、作業と観察は同じケースに残す。成果物は実験を終えた後も同じ場所で使える。

## 取得

単独で使う場合は、実験リポジトリを clone する。

```sh
git clone https://github.com/fdshg693/AI-experiments.git
cd AI-experiments
```

アンブレラと一緒に使う場合は、そのルートで `just sub-init`、`just links-sync`、`just sub-hooks-install` を実行する。共有 plans とコミット手順へのリンクが作られ、共通の Git フックを利用できる。ケースの開始・再開は単独 clone でも同じ手順で行える。

## 構成

```text
README.md                    実験の運用手順
AGENTS.md                    エージェント向け指示
CLAUDE.md                    AGENTS.md への参照
scaffold/README.md           ケース開始時にコピーする雛形
cases/<目的を表す名前>/
  README.md                  目的、現在地、観察、原本への反映判断
  work/                      導入したもの、日々の作業と成果物
  notes/                     長い観察記録が必要になったときに作る
```

## 始める

1. 達成したいことからケース名を決める。リポジトリのルートで次を実行する。雛形の例は自分のケースの内容に置き換える。

   ```sh
   case_dir=cases/find-past-decisions
   mkdir -p "$case_dir/work"
   if [ ! -e "$case_dir/README.md" ]; then
     cp -n scaffold/README.md "$case_dir/README.md"
   fi
   ```

2. 目的、現在の問い、次に試すことを書く。問いがまだ定まらなければ「使いながら探る」で始めてよい。振り返る節目はここで決めるか、使いながら決める。
3. 原本ごとにリポジトリ・パス、導入するコミット、役割を記録する。その版の原本の導入手順に沿って `work/` に取り込む。アンブレラと一緒に開いている場合も、単独で開いている場合も、対象欄のリポジトリとコミットから同じ版を特定できるようにする。
4. 実データを使う前に、保存先と公開範囲を確認する。共有できないデータは ケースの `private/`（Git の除外対象）か、アクセス制限のある保管場所に置く。ケース README には共有できる要点と、共有できる成果物への相対リンクを残す。

## 使う・再開する

普段の作業は `work/` で進める。困ったことや判断が変わったことがあれば、日付、試したこと、起きたことと根拠へのリンクを観察欄に追記する。長い観察は `notes/` に書き、観察欄からリンクする。対象を追加・変更した日付と理由を記録し、導入した版の履歴を残す。保存先の公開範囲に合わせて作業と成果物をコミットできる。

別のセッションで再開するときはケース README を開き、「目的と現在地」の次の一手を起点にする。「対象」で導入版を確認し、「観察」のリンクから成果物を開く。「原本への反映」で次に見直す発見と判断条件を確認する。再開したら状態を「進行中」にし、問いや次の一手を更新する。

## 振り返る・原本に反映する

- 「過去の判断を初めて探し直した時」など、目的に沿った節目に振り返る。詰まった箇所、作業場で試した直し方、成果物への影響を確かめる。明確な手順ミスは判明した時点で扱う。
- 発見ごとに反映先と判断を記録する。同じ発見から複数の原本を見直す場合は反映先ごとに行を作る。判断を保留する場合は、再確認する時機と、その時までに分かっていてほしいことを書く。
- 他の利用者にも役立つ改善は、共有可能な例と期待する効果を添え、原本のリポジトリの手順に従って提案する。ケース固有の事情は理由とともにケースに残す。提案は実験の途中でも行える。
- 採用後は PR または反映コミットを記録し、新しい版をケースに取り込む。対象欄に更新日と理由を足し、実際の作業で効果を確認して観察欄に残す。

## 休止する・終了する

休止時は状態を「休止」にし、再開するときの次の一手を書く。終了時は状態を「終了」にし、得られた結論を書く。どちらの場合も、まだ判断していない反映候補と、継続利用する成果物の場所をケース README に残す。

## 記入例

### 単一対象で設計判断を後から探す

- **目的と現在地** — 仕様変更のときに以前の判断理由へたどり着く。問いは「置き換え前の判断も探せるか」。進行中。次は古い仕様を一件選び、現行の判断までたどる。最初に探し直せた時点で振り返る。
- **対象** — [fdshg693/AI-templates](https://github.com/fdshg693/AI-templates) の `core/decisions/`、`cbdf5590dba9b29d51e5de9171f2ab31d0f4d9f8`。変更理由と置き換えの履歴を `work/decisions/` に残す。

### 複数対象で調査から設計判断までを残す

- **目的と現在地** — 採用したサービスの選定理由を調査資料までさかのぼる。問いは「判断から比較の根拠を見つけられるか」。進行中。次は候補二件の比較メモを一つの設計判断から参照する。
- **対象** — いずれも [fdshg693/AI-templates](https://github.com/fdshg693/AI-templates) の `cbdf5590dba9b29d51e5de9171f2ab31d0f4d9f8`。
  - `core/knowledge-vault/` は調査資料と比較を `work/vault/` に残す。
  - `core/decisions/` は採否と理由を `work/decisions/` に残す。
- **原本への反映** — decisions の書き方ガイドへの根拠リンク例は「提案」。比較メモから設計判断への逆引きは knowledge-vault への候補として「観察中」。二件目でも逆引きが必要になった時に再判断する。
